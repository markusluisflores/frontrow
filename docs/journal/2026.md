# frontrow — Session Journal 2026

## 2026-09-17 — Project Brainstorm & Design Session

**Decisions:**

- **The project's purpose is backing an unbacked resume claim, not "Spring Boot is in demand."** Reading `markusluisflores.github.io/src/_data/resume.json` showed `Java` listed under Backend skills with no supporting bullet anywhere — Infor was LPL (proprietary), RBC is SDET/Playwright/Postman, the SAIT capstone was Next.js, Carpool was Laravel/PHP. Every other listed skill has evidence; Java is the one load-bearing claim without any. That reframing is stronger than the market-demand argument Markus started with and it drove every scope decision after it.
- **One project with two inbound adapters, not two projects.** Markus asked whether Spring Boot and MCP could be the same thing. They can, and the architecture is what unites them rather than stapling them: a domain core with a REST adapter and an MCP adapter over the same application services. The load-bearing sentence is "MCP is just another inbound adapter — the domain doesn't know it exists," which reads as ports-and-adapters discipline to a Java reviewer and as a correct understanding of MCP to an AI-platform reviewer. Rejected: two separate repos (each gets half the depth, and a standalone MCP server with no domain of its own is a toy).
- **Domain criteria were corrected mid-session after Markus pushed back.** The first three domain options were all drawn from his own work history (trading/IMS, HCM leave, football). He asked why. The honest answer is that prior experience only buys easier "why did you model it that way" answers — a modest edge — while the domain is *not* what's being assessed, familiarity across four projects can read as narrowness, and the strongest predictor of a solo project existing is wanting to build it. Criteria revised to two hard ones: real business rules (not CRUD), and genuine agent value. Prior experience demoted to a tiebreaker.
- **Event ticketing / seat reservation chosen** because concurrency under contention is the single problem that *earns* the rest of the checklist: it justifies Testcontainers integration tests, real transaction reasoning, and a clean read-vs-write split for MCP tools. Rejected: warehouse inventory (overlaps the Orbit capstone, risks reading as repetitive) and beekeeping hive management (personal and memorable with the best odds of being finished, but earns fewer enterprise checklist items naturally — thinner security story, less reason for event-driven work).
- **The invariant lives in the schema, not in a service method.** A Postgres partial unique index on `seat_hold (event_seat_id) WHERE status = 'ACTIVE'` plus a unique constraint on `order_line(event_seat_id)`. Chosen over optimistic locking or pessimistic `SELECT ... FOR UPDATE` as the primary guarantee because it makes double-booking physically impossible even if application logic is wrong. Application code translates the constraint violation into a structured `seat_taken` error. Owed an ADR (see Pending).
- **Hold expiry uses two mechanisms deliberately** — lazy in-transaction expiry for correctness, plus a scheduled sweeper for hygiene — so correctness never depends on the scheduler running. Being able to explain why both exist is the point.
- **No `confirm_order` MCP tool. An agent can hold seats; only a human can buy them.** Holds are reversible and expire on their own; purchases are neither. This is the project's threat model in one line and its sharpest interview claim. Owed an ADR (see Pending).
- **API-only, no frontend** (Markus's call). Four existing portfolio projects already prove frontend ability; OpenAPI/Swagger UI plus seeded data plus the MCP server is the demo, so all effort concentrates on the actual gap.
- **Kafka, the Prometheus/Grafana observability stack, and OAuth2 are explicitly out of Phase 1** despite all three being named in-demand by the research. Markus wants something presentable in days-to-a-week; including them produces a half-finished everything, which the same research says is strictly worse than a small complete thing. All three are scheduled as Phases 2–3.
- **Research changed two things materially, so it was worth running rather than reasoning from priors.** (1) MCP portfolio projects are *not* generic — there is a specific published bar (typed schemas checked in, at least one logged tool failure, thin single-responsibility tools, structured error contracts with recovery hints, architecture diagram with threat model, measured success rate and p95). That bar is a testing-and-observability checklist wearing an AI hat, which plays directly to Markus's SDET background. (2) Testcontainers is repeatedly named as *the* differentiator between strong and weak Spring developers, and observability is missing from ~70% of Java resumes.

## 2026-09-18 — Requirements Review, Bootstrap, and Seven-Round Spec Revision

**Decisions:**

- **Bootstrapped the repo before revising the spec, rather than editing the untracked file in place.** The global rule puts every spec revision on its own `docs/` branch with a PR review, and a revision with no diff history would be unreviewable. The original design docs went in as their own first commit, so revision 2 shows as a real diff.
- **Public repo** (Markus's call): it's a portfolio project, and public repos get free secret scanning, push protection and branch protection. The pre-commit hook blocks local device paths and runs gitleaks; both were tested in both directions before the first push.
- **Stack-specific bootstrap deferred to the scaffold task.** Maven wrapper, Spotless, CI, CodeQL and Dependabot all need a `pom.xml`. Scaffolding one early to tick boxes would pre-empt the Phase 1 plan. The deferred list sits in `CLAUDE.md`, so the scaffold task can't silently drop it.
- **Dropped stdio and SSE for Streamable HTTP** (Markus confirmed). SSE is deprecated in the MCP spec and in Spring AI 2.0.0 (checked against the Spring AI docs). Stdio had nowhere to authenticate a caller, which was the open question blocking the per-caller guardrails and `release_hold`. It would also have run a second JVM beside `docker compose`, with duplicate sweepers and stdout corruption risk. HTTP gives a real bearer-token identity, and Claude Code supports HTTP servers, so no client reach is lost.
- **Claim index covers `ACTIVE` and `CONVERTED`.** With `ACTIVE` alone, a sold seat had no active hold, so the schema prevented a double sale but not a new hold on a sold seat. The project's central claim ("the schema, not the app") was only half true until this changed.
- **"Agent holds, human buys" made enforceable, not just stated.** It now rests on two disjoint filter chains: bearer only on `/mcp`, Basic only on `/api/**`, plus an explicit 401 filter because Spring's Basic filter silently ignores bearer headers. Revision 1 never designed the handover itself; it's now a shared owner identity plus `GET /api/me/holds`.
- **One global lock order** (idempotency key → owner advisory lock → event row → seat rows ascending). This came out of review rounds 2–4, not the first draft. The event-row lock fixes the cancel-vs-confirm race. Taking it anywhere but before the seat locks would deadlock. Hold creation must finish one seat before starting the next, or the order breaks across a lock phase and an insert phase.
- **Order cancellation, venue CRUD and public deploy became explicit non-goals.** Each would have silently weakened a guarantee: the permanent sold-once constraint, the seed-only seat maps, and demo-grade credentials on a public URL.
- **The review loop stopped on the rule, not on fatigue.** Every fix pass got a resumed + fresh reviewer pair. There were seven rounds, with blockers of 2, 1, 2, 1, 0, 1, 0. The round-6 blocker was a false claim *I* had introduced in round 5 by adopting a reviewer's Hibernate statement without checking it. The closing pair's one wording nit was deliberately left out of PR #1, so no unreviewed edit followed the closing pair. It was applied in the wrap-up PR (#2), once the interview-guide accuracy check found the spec contradicting the guide.
